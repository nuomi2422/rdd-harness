### 3.4 重新启用步骤（按此顺序，★ server 必须先起）

```
① 起 server：cd mc-openclaw-controller && node scripts\server.js      ← 必须先
② 游戏必须在跑，且 mods/ 里有 client_controller jar，配置 auto.connect=true
③ 探活：node scripts\oc-send.js --probe
④ 看同伴：node scripts\watch-ai.js --from-rdd --dist 6
```

> ❗ **mod 不会重连**：只在 client setup 时连一次 WebSocket，server 后启动就永远连不上。→ **先起 server 再开游戏**。
> ❗ **两个 jar 陷阱**：`build\libs\` 那个（151 KB，0 flatten、0 module-info）是干净版；`mods\_disabled\` 里那个（375 KB，flatten 了 100 个 `org.java_websocket` + 带 module-info）**装了会让游戏崩**（`ResolutionException`，与 NeoForge 的 `mixinextras.neoforge` 撞 split package）。
> ❗ **`watch-ai.js` 在这个「已存档」的仓库里，不在 rdd-selfcompile 下**，且 `mc-watch.js` 硬编码调它 → 动这个仓库前先问用户。

### 4.2 五个模式

| 模式 | 语义 | 实现 |
|---|---|---|
| `OFF` | 关闭，`isActive()` 假 | — |
| `SHOULDER` | **越肩**：镜头贴目标背后 | `MixinCamera.java:118` |
| `ORBIT` | **轨道**：目标半径固定，机位转，目标持续入画 ← **当前配置** | `MixinCamera.java:126-133` |
| `LOCK` | **固定机位**：锁 `lock.x/y/z`，只转镜头不动位 | `MixinCamera.java:139-142` |
| `CINEMATIC` | **电影**：越肩 + 俯仰偏移 + 连拍阻尼（λ=0.15） | `MixinCamera.java:149-155` |

`holdWhenLost=true` → 目标不可见（距离/墙）时用 `dampedPosition()` 顶住最后机位。

## 9 · ★★★ 实测使用方法（2026-10-03 22:46~23:13 全部真跑过一遍）

### 9.1 起游戏（⚠ 这条路踩了 3 个坑才通）

```powershell
# ❌ 坑 A：AGENTS 第 −1 条推荐的姿势，在 opencode shell 里【不存活】
Start-Process node -ArgumentList '...\mc-start.js gpt 120' -WindowStyle Minimized
#    实测两次：node 进程秒退、descendants=0、java=0、latest.log 零增长

# ❌ 坑 B：前台跑会阻塞（>100s 被 shell 工具杀掉）
node rdd-selfcompile\scripts\mc-start.js gpt 120

# ✅ 唯一实测能起来的姿势
Start-Process powershell.exe -ArgumentList @(
  '-NoProfile','-ExecutionPolicy','Bypass','-File',
  '"E:\restart developing doer\rdd-selfcompile\scripts\launch-mc.ps1"',

```

**⚠ 坑 C（最反直觉的）**：上面这条命令 opencode shell 会报 `ChildProcess.kill` 之类的错，
**但 Start-Process 其实已经执行了，游戏真的起来了**（实测 22:46:46 java pid 33316 起来）。
**「工具报错」≠「命令没跑」—— 必须自己复核进程，不能凭报错就重发。**

复核命令（返回即出，不阻塞）：
```powershell
node rdd-selfcompile\scripts\mc-start.js --status
# 实测输出：java=1 log=451388B lock=02:50:44 mcp=1 空闲=793MB
# ⚠ lock 那列是死的（bug-4），别当判据；java= 和 mcp= 可信
```

启动器 bat 在 live 实例的 **`shaderpacks\` 目录**下（`config.ps1:50` 用 glob 发现，名字含中文），
live 实例 = `E:\.minecraft\versions\The Best of Twilight Forest`，存档名 `live`。

**⚠ 坑 D**：`node mc-start.js` 必须用 `node`，不能用 `powershell -File`（会报「不是 .ps1」）。
`launch-mc.ps1` 在游戏已跑时**正确拒绝二次启动**（输出 `LAUNCH_CHECK running=1` → `LAUNCH_SKIP_ALREADY_RUNNING`，exit 2）。

### 10.4 牵引（ CompanionTether ）的设计与实测

**判据**：`CameraRig.resolveTarget() == null` 连续 **40 tick（2 秒）** 才判「走出加载区」。
为什么不是一次就传 —— 否则「刚传过去 → 那一格还没加载 → resolveTarget 还是 null → 再传」
会变成每 2 秒传送一次的抖动死循环。

**冷却**：每次传送后 **100 tick**。

**传送走坐标不走名字**：`/tp @s <x> <y> <z>`。
按名字传（`/tp @s DDD`）会落在它**脚下正中**，它站在窄处/墙边时会把玩家挤进方块里。

**权限**：无 `hasPermissions(2)` 时明确回「单人游戏要开作弊」，**不静默失败**。

**`mc.screen != null` 时不动玩家** —— 你在开 GUI 的时候不该被拽走。

**实测**（`th-04-final.png`）：
`牵引 超出 18 格 → 已发 /tp 过去 → /tp @s 528.0 64.0 1352.8`，随后 ACX 变成「在 2 格外（渲染范围内）」。

| baseline | 528.03 → 536.44 = **8.41 格** | 4.2 格/s | — |
| `/cam run true` | 536.44 → 547.1 = **10.66 格** | 5.3 格/s | **+27%** |

**为什么疾跑用 `setSprinting(true)` 而不是 `keySprint.setDown(true)`**：
原版疾跑还有 5 个前置条件，其中一个是 **7 tick 的 `sprintTriggerTime` 窗口**
（`LocalPlayer.java:774-783`），按下 `keySprint` 只是「获得许可」，还得等窗口。
每 tick 直接 `setSprinting(true)` 才真的立刻生效 —— 「不然看着卡」这条被它解决。

**飞行必须每 tick 重申**：原版 `LocalPlayer` 有

→ **一落地就自动关飞行**。所以 `FastMove.setFly` 每 tick 重申
`mayfly=true; flying=true; onUpdateAbilities()`。

### 10.6 录像（VideoRecorder）—— 首测 2 个 bug，修完全绿

**产物**：`screenshots\numencam_<yyyyMMdd-HHmmss>\`
= `f_00000.png … f_00159.png` + `numencam.txt` + `ffmpeg.log` + `numencam.mp4`

**★ 实测终态**（`numencam_20261004-015346`）：
```
numencam.txt :: fps=10 | frames=160 | dropped=0 | failed=0 | duration_s=16
numencam.mp4  787,532 B
Duration: 00:00:16.00   Stream: h264 (High) yuv420p 854x480 10fps 392kb/s
frame= 160 fps=62 speed=6.13x        ← 160 帧全编进去
```
（已用 `ffmpeg` 反抽第 0/80/159 帧存图核对，画面确有走动内容，不是定格。）

**★★ 首测踩的两个坑（都已修）**：

1. **帧号缺口 → ffmpeg 只编出 1 帧。**
   第一版拿「抓帧序号」当落盘文件名，去重后留下 `f_00000, f_00010, f_00011, …, f_00068` 这种缺口。
   **ffmpeg 的 image2 解码器把 `%05d` 当连续序列读，遇到第一个缺口就停** → `frame= 1`。
   修法：新增 `outIndex`（落盘序号，与 `frameIndex` 抓帧计数分开），文件名用 `outIndex++`。
   **⇒ 这条是「看起来成功、其实产物废了」的典型：回执和文件都在，只有 ffmpeg.log 里的一行 `frame=` 暴露真相。**

2. **去重默认开启 → 8 秒 10fps 只落 12 张（`dropped=70`），视频成了 1.2fps 定格动画。**
   站着不动画面完全静止，8×8 采样点哈希把所有重复帧都丢了。
   修法：`dedupe` 默认 **false**；`start(fps)` 委托给 `start(fps, false)`；
   `/cam rec start [fps] [dedupe]` 可以手动开。类注写明理由：
   「录视频要的是连续时间轴，站着不动也是一段真实画面」。

**两个必须记住的实现要点**：
- **抓帧在主线程（tick 驱动，每 N tick 一次）→ GL 读回用 `RenderSystem.recordRenderCall`**；
  `NativeImage.writeToFile` 扔 `Util.ioPool()` 线程做（否则磁盘 IO 堵渲染）。
- **`img.close()` 必须放在 IO 任务的 finally 里**，放早了下一帧读到已释放内存 → 整段视频花掉。

**ffmpeg 探测**：先 `PATH`，再扫
`~/AppData/Local/Microsoft/WinGet/Packages/*FFmpeg*/**/ffmpeg.exe`（**不写死版本号**）。
本机命中 `ffmpeg-8.1.1-full_build\bin\ffmpeg.exe`。
编码参数：libx264 + yuv420p + `-vf scale=trunc(iw/2)*2:trunc(ih/2)*2`
（**yuv420p 要求偶数宽高**，MC 主渲染目标不保证是）。

**封盘三步全异步**（`SEAL_WAIT_IO` → 写 `numencam.txt` → 守护线程起 ffmpeg → `SEAL_WAIT_FFMPEG`），
所以 `/cam rec stop` 立刻回执，不等编码。**要拿 mp4 得等几秒。**

### 10.7 ★ 又发现并修掉一个「工具一直是坏的」（bug-8）

`oc-send.js --walk` 的 `posOf` 写死了
`/"position":\{"z":…,"y":…,"x":…/ `，
但 mod 侧用 `java.util.Map.of(...)` —— **`Map.of` 的迭代顺序是 JVM 次序随机化（SALT）**，
所以这次回 `x,y,z`、上次回 `z,y,x`。
结果：`--walk` 几乎总是走 pos parse failed、退出码 8，**位移判据形同虚设**
（实测三次走位全部报 parse failed，而底层坐标明明在变 8~19 格）。

**修法**：先切 `"position":\{([^}]*)\}`，再按 key 名取 `x` / `y` / `z`。
**修完实测**：`WALK key=w 1500ms from(528,64,1352.8) to(532.05,64,1343.06) moved=10.55 blocks => MOVED ✔` exit 0。

> **这条的教训比 bug 本身重要**：`--walk` 从 2026-09-30 起就一直「exit 0 但位移判据无效」，
> 而**没人发现**，因为它失败的方式是「报 parse failed」而不是「报错」。
> ⇒ 凡是「解析上游 JSON 再算判据」的脚本，都要先确认**上游 JSON 的字段顺序真的稳定**。
